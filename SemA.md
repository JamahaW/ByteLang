# Архитектура семантического анализатора MizLang

## Философия дизайна

Семантический анализатор для MizLang должен быть **модульным**, **расширяемым** и **отказоустойчивым**. Он должен собирать все ошибки, а не падать при первой же, и обеспечивать качественные
диагностические сообщения.

## Основные концепции

### 1. **МНОГОПРОХОДНОСТЬ**

Анализатор работает в несколько проходов, каждый со своей задачей:

```
Исходный код → Парсер → AST → СемАнализ → Успех/Ошибки
```

### 2. **РАЗДЕЛЕНИЕ ОТВЕТСТВЕННОСТИ**

Каждый компонент отвечает за свою часть семантики:

| Компонент     | За что отвечает                   |
|---------------|-----------------------------------|
| Symbol Table  | Хранение и поиск символов         |
| Type System   | Проверка типов и совместимости    |
| Flow Analyzer | Проверка потока управления        |
| Init Checker  | Проверка инициализации переменных |

### 3. **КОНТЕКСТНЫЙ АНАЛИЗ**

Анализатор отслеживает контекст:

- **Текущая область видимости** (scope)
- **Текущая структура** (для Self)
- **Текущая функция** (для return)
- **Глубина циклов** (для break/continue)

## Архитектурные компоненты

### **1. СИСТЕМА ТИПОВ (Type System)**

#### Иерархия типов:

```
Type (базовый)
├── BuiltinType (int, real, string, void, bool)
├── StructType (пользовательские структуры)
├── FunctionType (сигнатуры функций)
├── ArrayType (массивы)
├── SliceType (срезы)
├── PointerType (указатели)
└── SelfType (специальный тип для структур)
```

#### Особенности:

- **Типы как значения первого класса** - можно присваивать переменным
- **Self resolution** - `Self` разрешается в текущий тип структуры
- **Type inference** - вывод типов для переменных (где возможно)
- **Structural vs nominal typing** - как сравниваем типы?

### **2. ТАБЛИЦА СИМВОЛОВ (Symbol Table)**

#### Структура:

```
SymbolTable
├── Scope (область видимости)
│   ├── symbols: Map<name, Symbol>
│   ├── parent: Scope
│   └── children: List<Scope>
└── current_scope: Scope
```

#### Виды символов:

- **VariableSymbol** - переменные (`var`)
- **TypeSymbol** - псевдонимы типов (`def Name = Type`)
- **FunctionSymbol** - функции (`def Name = fn(...)`)
- **StructSymbol** - структуры (`struct`)
- **FieldSymbol** - поля структур
- **ParameterSymbol** - параметры функций

#### Механизм разрешения (resolution):

1. Поиск в текущем scope
2. Поиск в родительских scopes (рекурсивно)
3. Глобальный scope

### **3. АНАЛИЗАТОРЫ (Analyzers)**

Каждый анализатор - независимый компонент:

#### **3.1 Declaration Collector**

**Цель**: Собрать все объявления в таблицу символов

**Процесс**:

```
Для каждого объявления в AST:
  1. Определить вид символа
  2. Проверить уникальность имени в scope
  3. Добавить в таблицу символов
  4. Для структур: создать отдельный scope
```

#### **3.2 Type Checker**

**Цель**: Проверить корректность всех выражений с точки зрения типов

**Методы**:

- **Type inference** - вывод типа выражения
- **Type compatibility** - можно ли присвоить тип A типу B
- **Operator checking** - проверка операций (+, -, *, / и т.д.)

**Правила проверки**:

1. Литералы имеют явные типы
2. Идентификаторы должны быть объявлены
3. Операции требуют совместимых типов операндов
4. Вызовы функций проверяют аргументы
5. Присваивания проверяют совместимость

#### **3.3 Control Flow Analyzer**

**Цель**: Проверить корректность управляющих конструкций

**Проверки**:

- `break`/`continue` только внутри циклов
- `return` только внутри функций
- Все пути функции должны возвращать значение (если не void)
- Нет недостижимого кода

**Состояние**:

```python
{
    "in_loop": boolean,
    "in_function": FunctionType,
    "has_return": boolean,
    "current_loop_depth": int
}
```

#### **3.4 Initialization Analyzer**

**Цель**: Проверить инициализацию переменных перед использованием

**Метод**:

- Отслеживать, какие переменные инициализированы
- Для каждого чтения переменной проверять, что она инициализирована
- Учитывать все возможные пути выполнения

#### **3.5 Memory Safety Analyzer** (опционально)

**Цель**: Проверка явного управления памятью

**Проверки**:

- `&x` - x должен быть lvalue
- `*p` - p должен быть указателем
- Нет dangling references
- Все allocated memory освобождается

### **4. КОНТЕКСТНЫЙ МЕНЕДЖЕР (Context Manager)**

Отслеживает текущий контекст анализа:

```py
class AnalysisContext:
    current_scope: Scope
    current_function: Optional[FunctionSymbol]
    current_struct: Optional[StructType]
    loop_depth: int
    return_type: Optional[Type]
    self_type: Optional[Type]  # Текущий Self
```

## Этапы работы

### **ЭТАП 0: ИНИЦИАЛИЗАЦИЯ**

1. Создать таблицу символов
2. Зарегистрировать встроенные типы (int, real, string, void)
3. Создать глобальный scope

### **ЭТАП 1: СБОР ОБЪЯВЛЕНИЙ (PASS 1)**

```
Вход: AST
Выход: Symbol Table (полная)
```

**Порядок обхода**:

1. Глобальные объявления (def, var, struct)
2. Для каждого struct:
    - Создать новый scope
    - Добавить Self символ
    - Собрать поля и методы
3. Для каждой функции:
    - Собрать параметры
    - Пока не проверять тело

### **ЭТАП 2: ПРОВЕРКА ТИПОВ (PASS 2)**

```
Вход: AST + Symbol Table
Выход: Типизированный AST + Ошибки типов
```

**Правила обхода**:

1. Листья (литералы, идентификаторы)
2. Выражения снизу вверх
3. Для каждого узла:
    - Вывести тип
    - Проверить совместимость с контекстом
    - Сообщить об ошибках

### **ЭТАП 3: ПРОВЕРКА ПОТОКА (PASS 3)**

```
Вход: Типизированный AST
Выход: Ошибки потока управления
```

**Метод**:

1. Отслеживать вход/выход из функций, циклов
2. Проверять break/continue/return
3. Анализировать достижимость кода

### **ЭТАП 4: ПРОВЕРКА ИНИЦИАЛИЗАЦИИ (PASS 4)**

```
Вход: AST с информацией о путях выполнения
Выход: Ошибки инициализации
```

**Метод**:

1. Data-flow анализ внутри каждого scope
2. Отслеживать присваивания
3. Проверять чтения переменных

## Обработка особенностей MizLang

### **1. Self в структурах**

**Механизм**:

```
Внутри struct:
  - "Self" → текущий тип структуры
  
Внутри метода:
  - Параметр "self: Self" → получает тип структуры
  - Параметр "self: *Self" → получает PointerType(структура)
```

**Процесс**:

1. При входе в struct scope добавляется символ Self
2. Self разрешается в текущий StructType
3. При проверке методов:
    - Первый параметр должен быть `self`
    - Тип Self заменяется на фактический тип структуры

### **2. Типы как выражения первого класса**

**Пример**:

```mizlang
def IntType = int          // Тип как значение
def IntPtr = *int          // Указатель как тип
def FuncType = sig(int)real // Сигнатура как тип
```

**Обработка**:

1. При сборе объявлений:
    - Если RHS - TypeExpression → создаем TypeSymbol
    - Иначе → создаем VariableSymbol
2. При проверке типов:
    - TypeSymbol может использоваться в контексте типа
    - VariableSymbol содержит значение типа

### **3. Метапрограммирование**

**Подход**: Двухэтапный анализ

```
def Matrix = [10][10]real  // Этап 1: Собрать как тип
def size = 10              // Этап 1: Собрать как значение
def Array = [size]int      // Этап 2: Проверить, что size вычисляется в compile-time
```

### **4. Явное управление памятью**

**Проверки**:

- `&expr` - expr должен быть lvalue
- `*expr` - expr должен быть указателем
- Присваивание указателей проверяет типы
- Нет арифметики указателей (если не предусмотрено)

## Обработка ошибок и диагностика

### **Принципы**:

1. **Не падать на первой ошибке** - собирать все ошибки
2. **Контекстные сообщения** - указывать позицию и контекст
3. **Предложения по исправлению** - где возможно
4. **Ворнинги** - не критические проблемы

### **Виды ошибок**:

1. **Семантические ошибки** (критические):
    - Необъявленный идентификатор
    - Несовместимость типов
    - Неправильное использование break/return

2. **Предупреждения** (не критические):
    - Неиспользуемая переменная
    - Мертвый код
    - Возможная ошибка инициализации

## Интеграция с существующей системой

### **Связь с парсером**:

```
Parser → AST → SemanticAnalyzer → (успех или список ошибок)
```

### **Расширение AST**:

AST может быть расширена:

- Добавление `type` поля к Expression узлам
- Добавление ссылок на Symbol в Identifier
- Добавление scope информации

## Стратегия реализации

### **Инкрементальный подход**:

1. **Минимальный работающий анализатор** для простых программ
2. **Постепенное добавление** фич
3. **Регрессионное тестирование** на каждом шаге

### **Приоритетность**:

1. Базовые типы и переменные
2. Функции и вызовы
3. Структуры и Self
4. Управление памятью
5. Метапрограммирование

### **Тестирование**:

- Юнит-тесты для каждого компонента
- Интеграционные тесты для полных программ
- Тесты на ошибки (negative tests)

## Резюме архитектуры

Семантический анализатор MizLang - это **многопроходная, модульная система**, где каждый компонент отвечает за свою часть семантики. Она строится вокруг **таблицы символов** и **системы типов**, с
дополнительными анализаторами для **потока управления**, **инициализации** и **безопасности памяти**.

**Ключевые инновации**:

1. Self как явный параметр с полной типизацией
2. Типы как значения первого класса
3. Двухэтапный анализ для метапрограммирования
4. Явное управление памятью с проверками

Эта архитектура обеспечивает **строгую типизацию** при сохранении **гибкости** для метапрограммирования и **безопасности** для явного управления памятью.
